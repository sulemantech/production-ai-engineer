## Track 1 Week 1 Day 4 — Loop guards / infinite loop prevention
**Q:** Why would an agent loop infinitely, and how do you prevent it?
**A (as given):** "the agent loop would run infinitly because it should be active all time, the user request can ocme anytime and it should be ready to serve the user request accoridngly. After serving the user request it should be in wiating for the command phase it should not be consuming the resources in that case and should stay idle."
**Feedback:** Answered a different question than the one asked — described service-level uptime/idle behavior (a server staying alive between requests), not the actual failure mode: the tool-use `while` loop *within a single agent turn* failing to terminate. Real causes to lead with: (1) a code bug where the loop's exit condition depends on a value nothing inside the loop reassigns — this happened for real in `day2_tool_agent.py`/`day3_multi_tool_agent.py`'s early drafts, a strong concrete example to use in an actual interview; (2) the model legitimately keeps deciding to call tools without ever reaching a stop condition, due to ambiguous instructions or unhelpful tool results. Prevention: max-iteration cap, wall-clock timeout, and tool results designed to actually let the model converge. Retry before moving to the next question — this one is worth re-answering cleanly since it's foundational and reappears in the Week 1 Assessment Gate scenario ("your agent called a tool 40 times in a row — diagnose it live").

**Reference answer (say this out loud until it's natural, adapt with your own words):**
> "The tool-use loop in my agent keeps calling the model, checking if it wants to call a tool, dispatching that tool, and feeding the result back — repeating until the model's `stop_reason` says it's done. It loops infinitely when that exit condition never gets satisfied. There are two ways that happens: one is a code bug — I actually hit this myself, where my `while` loop checked `response.stop_reason`, but nothing inside the loop reassigned `response` after dispatching a tool, so the condition just stayed true forever regardless of what the model actually wanted. The other is the model itself never converging — it keeps deciding a tool call is needed because the instructions were ambiguous or the tool result didn't actually give it what it needed to answer. I prevent both with a hard iteration cap and a wall-clock timeout as a backstop, independent of whatever the model decides to do, plus making sure tool results are actually useful enough that the model can converge instead of retrying blindly."

## Track 1 Week 1 Day 4 — User message → tool call execution walkthrough
**Q:** Walk me through what happens between a user message and a tool call executing, step by step.
**A (as given):** "1) User prompt 2) It goes directly to claud 3) If claud needs any tools to be used from the existing curated ones. It trying to use it and it keep on using the tools until it hit the stop ready or the guard rails stop the agent loop. 4) The end response is returned"
**Feedback:** Got the coarse shape right (prompt → possible tool use → loop → final answer) and correctly folded guardrails into the exit condition — good instinct. But skipped the load-bearing middle mechanics: (1) tool schemas are sent to Claude on every single call, not persistent knowledge; (2) the actual execution boundary — Claude only returns a `tool_use` block (id/name/input) requesting a call, it never executes anything, the application does — this is the single most important mechanic in the system and doubles as interview question #3 on this list, never skip it; (3) the round trip back appends *two* messages (Claude's own tool-call turn echoed back, plus a new tool_result turn matched by `tool_use_id`), not just "send the result." Also: say "stop_reason" precisely, not "stop ready" — small terminology slips undercut a hands-on signal. Same pattern as the Day 4 loop-guards question: strong shape at 10,000 feet, missing the mechanism underneath. Worth deliberately practicing zooming into the tool-call boundary specifically before the next attempt.

**Reference answer:**
> "The user message gets added to a messages array. I call the API with that array plus the full tool schemas — every request, not just the first one. Claude decides whether it needs a tool based on the message and those schemas; if it does, it comes back with stop_reason 'tool_use' and a tool_use block containing the tool's name and the input it wants to pass. Claude never executes anything itself — that's on my code. I look up the matching function, run it for real, and get a result back. Then I append two things to the conversation: Claude's own tool-call turn, and a new turn with a tool_result block tied to that call's id. I send the updated conversation back to Claude, and it either has enough to answer — stop_reason 'end_turn' — or it asks for another tool and the loop repeats, bounded by the iteration and timeout guards."

## Track 1 Week 1 Day 4 — Tool call vs. plain function call boundary
**Q:** What's the difference between a tool call and a plain function call in your code — where's the boundary?
**A (as given):** "tool call are the functions of which schema we share with the llm on every single to call to it. These are the functions that the llm can identitfy and our code shuoud in that case from the dispatcher, in the response the id and also the name is mentioned ot the tool to use next. Function on the other hand are the ordinary functions that our code can call anytime."
**Feedback:** Good improvement — correctly incorporated the schema-shared-every-call detail and the id/name dispatcher mechanics from the previous two rounds of feedback. But the core framing is still off: treated "tool function" and "ordinary function" as two separate categories of function, rather than recognizing it's the *same* function (e.g. `search_dtc`) called two different ways. The real boundary is about who decides to invoke it, not which bucket the function belongs to — a plain call is your code deciding directly; a tool call starts with Claude deciding at inference time and expressing that as data (a tool_use block: id/name/input) because it cannot execute code itself, and the dispatcher is the exact point where that data becomes a real function call. Also: Claude doesn't "identify" your functions — it never sees your code, only the name/schema you handed it.

**Reference answer:**
> "There's no functional difference between a tool call and a plain function call at the implementation level — same Python function either way. The difference is who decides to invoke it. A plain function call is something my own code decides to run, directly, as part of normal control flow. A tool call starts with Claude deciding, at inference time, that it wants a specific function run with specific arguments — but Claude can't execute code, so it can only express that as data: a tool_use block with an id, a name, and an input dict. My dispatcher reads that data and chooses to honor it by making an ordinary function call. So the actual boundary is the dispatcher itself — before it, you have a request encoded in JSON; after it, real code running, no different from anything else in the program."

## Track 1 Week 1 Day 4 — Handling malformed tool data
**Q:** How do you handle a tool that returns malformed data the model didn't expect?
**A (as given):** "In case the tools returns maleformed data the llm didnt expect, like the tool ended an exception, like this was an api and and it ended in 400+ error in the return http code. In thase case we return the response as is to the llm too. So that the llm knows it and laso decide what to do next."
**Feedback:** Right instinct (surface failure to the model rather than silently swallow it or crash), wrong framing ("as is"). Own codebase this week already proves the correct pattern: `dtc_lookup.py`'s None→`{"error": ...}` conversion, `vehicle_issues_lookup.py`'s try/except around `requests.exceptions.Timeout`/`RequestException` normalizing into a consistent success/error shape, and `day3_multi_tool_agent.py`'s dispatch loop converting any exception to `{"error": str(exc)}` — all three catch-and-normalize, never pass through raw exceptions/tracebacks/inconsistent API bodies. Genuine gap in both the answer and the actual code: never used `is_error: true` on the tool_result block — the API's structured way to flag failure as metadata rather than making Claude infer it from parsing content text. Worth adding to the real code, not just fixing in the next answer.

**Reference answer:**
> "I never let a tool's raw failure — an exception, a bad HTTP status — reach the model untouched. I catch it, and normalize it into the same clean shape my successful results use, usually an error field with a clear message, not a stack trace or raw response body. I also mark the tool_result block with is_error: true, so the model gets that as structured signal rather than having to infer failure from parsing text. That gives the model enough to actually react — retry with different input, try a different approach, or tell the user clearly — without ever seeing something malformed or unpredictable in shape."

## Track 1 Week 2 Day 4 — Human-in-the-loop interrupt: why and where
**Q:** Why would you want a human-in-the-loop interrupt in an agent, and where would you place it?
**A (as given):** "human in the agentic loop is very important because high risk and high stake decisions must be taken with the human permissions only. The interrups are using placed inside the graph during the decision"
**Feedback:** Right instinct on "why" — high-stakes/irreversible actions needing sign-off — but too vague without examples (irreversibility, cost/financial exposure, compliance, catching a hallucinated decision before it has real-world effect). "Where" was too vague to count as an answer ("inside the graph during the decision") despite having just built the precise answer in `day4_interrupt_graph.py`: after the model decides what it wants to do (need the actual tool + arguments to show a human) and before that action's side effects run — a dedicated node between the decision point and the execution node, exactly where `request_approval` sits between `model` and `tools`. Also missing: the checkpointer dependency (interrupt() has to persist state through what could be a long real-world gap before a separate Command(resume=...) call answers it).

**Reference answer:**
> "An agent that's fully autonomous doesn't fail by crashing — it fails by confidently doing the wrong thing with real consequences: deleting data, charging a card, sending a message to a customer. A human-in-the-loop interrupt exists to catch exactly that class of action — irreversible, costly, or compliance-sensitive — before it executes, not after. As for where: it has to sit after the model has decided what it wants to do, since you need the actual tool and arguments to show a human, and before that action's side effects run. In practice, that's a dedicated node between the decision point and the execution node — in LangGraph terms, exactly where I placed request_approval between model and tools. It needs a checkpointer behind it, since the pause has to survive potentially a long real-world gap before a separate call resumes it with the human's decision."
